# 设计与架构（dispatch 深度文档）

> 从根 README 迁入的深度内容：动机、核心概念、通道详解、架构、设计决策、项目结构。速览请回 [README](../README.md)。

## 动机

ZCode 提供多档模型（重思考 GLM-5.3、均衡 GLM-5.3-Flash、极速 GLM-5.3-FlashX、经 ListModels 可路由的任意模型）与两种并发原语（Agent 工具、CreateWorkflow）。宿主不回答的是调度问题：

1. **路由无依据。** 该不该并发、用哪个模型、开几路，没有评分标准时只能临场拍脑袋——不并发则慢，乱并发则有依赖的子任务互相踩踏。
2. **上下文单向污染。** 子代理的过程输出（读文件、跑命令、试错）若全量回流，主上下文被原始转储挤占，长任务后期质量下降。
3. **验收无纪律。** 快模型的结论偏浅、失败被静默重试、任务越拆越发散，没有统一的复核与收敛规则。

本插件以声明式文件为主（2 个代理定义、6 个命令、1 个技能）加一个确认闸钩子（hooks/confirm-gate.mjs，见 D8）把上述决策固化为「评分 → 确认 → 派发 → 回流 → 总装」流程。目标读者：配置了多个 provider、需要在 ZCode 中做受控并发的用户。

## 核心概念

理解以下三者的关系，是正确使用本插件的前提。

### 并发 ≠ 工作流

```
Agent 并发  = 同一回复内多路派发，子任务互不依赖
动态工作流  = 编排逻辑：依赖、分阶段、失败换档重试、大规模扇出
```

判据：**工作流吃的是结构，不是难度。** 有结构（下一步的输入来自上一步的输出）用 Agent 并发会卡在主会话中转；无结构上工作流是白付启动成本（写脚本 + 类型检查 + 后台运行）。

### 指挥官 ≠ 执行者

主 Agent 只做四件事：拆解、派发、验收、总装，不亲手做子任务。子 Agent 吃掉全部过程噪音，以固定格式回流：

```
结论 + 证据指针（路径:行号）+ 遗留不确定点
```

### 三个正交的决策

| 决策 | 谁拍板 | 机制 |
| --- | --- | --- |
| 通道（用哪个模型） | 评分推荐 + 用户确认 | AskUserQuestion，推荐项排第一 |
| 并发数 | 用户确认 | 按档位区间生成 下限/中位/上限 三选项，推荐下限 |
| 思考等级 | 仅工作流档 | `subagent_model` 加 `$low/$high/$max` |

三者互不依赖，可任意组合。主会话模型不在确认范围——由用户在模型选择器自选。

### 派发闭环

```
思考 ──► 派发 ──► 回流 ──► 再思考 ──► ……
                                ▲
                回流上限 2 轮，第 3 轮必须收敛交付
```

## 通道详解

| 触发方式 | subagent_type | 模型 | 默认并发（区间） | 回退 |
| --- | --- | --- | --- | --- |
| 默认并发 / flashx / 快速完成 / 速度优先 / 大批量 | `flashx-worker` | `magpie/auto/glm-5.3-flashx`（thoughtLevel high） | 4（4-8） | 无；缺失时提示检查，不静默降级 |
| flash / 要更稳结论的操作并发 | `flash-worker` | `magpie/auto/glm-5.3-flash` | 3（3-6） | `general-purpose`（已被 agents-state.json 固定为同模型） |
| 5.3 / 分身 / 高强度深挖 | `heavy-worker` | `magpie/auto/glm-5.3` | 2-4 | 无 |
| 工作流；点名其他模型；任务有依赖/循环/分阶段 | CreateWorkflow | 任意 ListModels ID（`subagent_model` 指定） | `max_concurrency` 硬限 | — |

任务画像 → 通道：

| 画像 | 通道 |
| --- | --- |
| 大批量、轻推理、求速率；图片输入、联网搜索 | flashx |
| 操作型并发，结论要求更稳 | flash |
| 多方案论证 / 逐文件审查 / 根因分析 / 攻防两条线 | heavy |
| A 群跑完再拆 B、失败自动换档重试、几百文件扇出 | 工作流 |
| 四维都低的小任务 | 主会话直接做，不派发 |

## 架构

### 调度链路

```
用户消息（触发词「并发/并行/分工/群集」│ 点名 │ 命令）
   │
   ├─ 命令 ────────────► 已点名通道，跳过评分确认 ─┐
   ├─ 自然语言 ──► swarm 技能                      │
   │              ├─ 四维评分 ──► 推荐通道          │
   │              └─ AskUserQuestion 确认 ─────────┤
   ▼                                               ▼
 主会话拆解（切分是思考的产物，互不依赖才并行）
   │  同一条回复内发出全部 Agent 调用（派发消息自包含）
   ▼
 子代理执行（过程噪音留在子上下文）
   │  回流：结论 + 证据指针 + 遗留不确定点
   ▼
 主模型验收总装（逐路过目 / 交叉验证 / 抽样复核）
```

### 四维评分

| 维度 | 锚点 |
| --- | --- |
| 散乱度 | 能否互不依赖地同时开工 |
| 依赖度 | 下一步的输入是否来自上一步的输出 |
| 规模 | 估出的子任务数，≥5 记高 |
| 思考难度 | 是否需要重推理 |

| 评分组合 | 推荐 |
| --- | --- |
| 有结构（依赖/分阶段/循环） | 动态工作流 |
| 散乱独立 + 操作型 | flashx（默认通道） |
| 纯难无结构 | heavy 分身 |
| 都低 | 主会话直接做 |

任一维度拿不准取更保守的一档，连同理由放进确认问。

### 声明式集成

`plugin.json` 声明 `agents/`、`commands/`、`skills/`、`hooks/` 四个组件：零 MCP、零独立运行时，唯一可执行脚本是确认闸钩子 `confirm-gate.mjs`（见 D8/D9）。定义随会话启动加载为快照（agent 定义在回合边界重扫，技能/命令需新会话）。

## 设计决策

九条核心决策，按 背景 → 决策 → 被否决方案 组织；标注版本号的为该版本的变更项。

### D1 · 派发前逐次确认，点名即视为回答

**背景**：并发消耗真实额度，路由决策不应因「早前确认过」而免检。
**决策**：每次派发前必须 AskUserQuestion 确认模型档与并发数；用户当前消息已点名**模型与并发数**时跳过——点名即回答，重复问是打扰；「以后都这样」仅修改默认推荐项，不免除逐次询问。
**被否决方案**：会话沿用（0.3.3 行为，确认一次后本会话不再问）——实测默认档在长会话中被静默固化，后续派发绕过用户，0.3.4 废弃。（2026-11-18 补充：仅点名模型未点名并发数时**不构成豁免**，仍须完整确认——漏问并发数被用户当场纠正过。）

### D2 · 默认通道 flashx，flash 保留给点名场景

**背景**：高频场景是「大批量、轻推理、求速率」的操作型并发，对单位成本与延迟敏感。
**决策**：未点名模型时派 flashx（1.3.4 起 magpie 中转，thoughtLevel high），默认 4 路；flash（默认 3 路）仅在点名或要求更稳结论时使用。
**被否决方案**：flash 作默认通道（0.3.3 行为）——成本与延迟偏高，与高频场景不匹配，0.3.4 对调。

### D3 · flashx 关键结论强制交叉复核

**背景**：flashx 速率优先、推理浅，汇报中的数字/事实/路径不可直接采信。
**决策**：影响决策的关键结论逐条过目，抽 1-2 条改派 flash 或 5.3 复核；不一致以复核为准并写进汇报。
**被否决方案**：直接采信——速率收益以结论风险为代价；全量复核——成本抵消并行收益。取抽样折中。（1.0.0 补充：汇总前的系统分级复核固化到 `/dispatch:collate`。）

### D4 · 回流两轮上限，第三轮强制收敛

**背景**：无上限的「回流→再拆」会发散——每轮产生新的不确定点，任务永不收敛。
**决策**：闭环最多 2 轮回流再思考，第 3 轮必须收敛交付，未决项如实标注。
**被否决方案**：无限迭代——发散风险不可控；单轮硬停——复杂任务确需二次拆解，一轮太紧。

### D5 · flash-worker 不内置，复用固定后的 general-purpose

**背景**：`~/.zcode/v2/agents-state.json` 已把 general-purpose 固定为 GLM-5.3-Flash。
**决策**：命令层「优先 flash-worker，缺则回退 general-purpose」，两者等效；本插件只定义 flashx-worker 与 heavy-worker。
**被否决方案**：内置 flash-worker 定义——同一模型两处定义、两处维护，且与本机固定配置可能漂移。

### D6 · 中转站代理显式声明 `thoughtLevel:`

**背景**：`$low` 后缀只在动态工作流 `subagent_model` 里生效，agent 文件不认。
**决策**：`new-provider` 等自定义 provider 的代理定义必须与 `model:` 并列写 `thoughtLevel:`（如 `thoughtLevel: low`），缺失时派发报 `reasoning-level-missing`。
**性质**：平台约束的规避项，不是可修复缺陷。

### D7 · 并发不限流，只给纪律区间

**背景**：Agent 工具没有并发硬上限；声明式组件无运行时强制点，确认闸（1.1.0）只管确认、不管并发数。
**决策**：给纪律建议区间 flash 3-6 / flashx 4-8 / heavy 2-4；唯一硬闸是工作流的 `max_concurrency`。
**被否决方案**：插件内限流——无执行点，假装能修不如如实记录（见 MAINTENANCE.md 平台约束）。


### D8 · 确认硬闸（1.1.0）

**背景**：「逐次必问」是 prompt 级软纪律，概率性被主模型跳过——直接派发无人拦截。
**决策**：PreToolUse(Agent|Task) 钩子 + exit 2 拦截**未确认的 dispatch 档位派发**；PostToolUse(AskUserQuestion) 写 10 分钟确认窗（同批共享）；点名豁免 = prompt 开头 `[named]`；应急关闸 gate.json。只拦档位类型，Explore/general-purpose 等官方自主代理不经过此闸。信任边界（第四轮审计成文）：闸防「忘了问」与未确认派发，不防拥有文件写权限的敌意模型——后者可直接写 gate.json/confirm.json 或伪造 `[named]` 自我豁免（见派发纪律第 8 条）；应急关闸仅应由用户手动操作。
**被否决方案**：继续纯软纪律——概率性跳过无法根除；拦所有 Agent 调用——误伤官方自主派发（Explore 搜索等）。代价：hooks 是会话快照，更新插件后需新会话生效。

### D9 · 硬闸边界补全（1.3.0）

**背景**：1.2.x 审计三项实锤——①命名空间 subagent_type（dispatch:flashx-worker）不在 GATED_TYPES，实弹绕闸；②mark 挂任意 AskUserQuestion，无关问题也开 10 分钟派发窗；③CreateWorkflow 不经闸但文档未言明。
**决策**：gate 先做命名空间归一化（`replace(/^.*:/,'')`）再比对；mark 增主题过滤（问题须含模型/档位/并发等要素才落标记，questions 缺失时防御性照写）；工作流档明示豁免（其确认由脚本→类型检查→用户确认流程自身承担）。
**教训（双源码树）**：push-repo 发布仓与装机源曾各自演化——1.1.0 的 README/docs 变更只落在发布仓。自此 workspace 插件源为唯一事实源，发布仓由发布流程从本目录生成，禁止双边编辑。
**被否决方案**：matcher 直接加 CreateWorkflow——闸无法校验工作流脚本内容，拦则误伤正规流程；mark 精确绑定问题-派发对——hook 层拿不到关联凭证，做不到干净的绑定。
